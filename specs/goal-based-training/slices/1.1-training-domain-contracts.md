# Slice 1.1: Training domain contracts and persistence

## Objective

Create the durable, owned data model needed to preserve a training profile,
starter provenance, user-owned programs, dated workout/set snapshots, idempotent
set mutations, and finalized day participation. Existing users and weekly-plan
data remain readable.

## Signal

**Signal Skill:** None

**Expected Behavior:**
- Migrations apply forward/backward on an empty database.
- An upgrade fixture at migration 011 preserves legacy logs/set history while
  removing date-only identity constraints.
- Model validation rejects unknown goals/statuses, invalid weekday lists, and
  invalid IANA timezone names.
- Unit tests prove required/extra set and immutable-history representations.

## Required outcomes

- Extend the profile/settings contract without breaking existing profile reads.
- Freeze these `/api/v1` resources in `docs/CONTRACTS.md` now: `training-profile`,
  `starter-programs`, `programs`, `schedule`, `scheduled-workouts`,
  `workout-sessions`, and `participation`. Document exact request/response/error
  shapes, `Idempotency-Key`, `expected_revision`, and 409 conflict responses.
- Canonical profile wire values are goals `general_health`, `strength`,
  `hypertrophy`, `conditioning`, `power`, `body_composition`; activity
  `sedentary|light|moderate|high`; experience
  `beginner|intermediate|advanced`; equipment drawn from
  `bodyweight|bands|dumbbells|barbell|machines|cardio_machine|full_gym`;
  duration 20..120 minutes; unique ISO weekdays 1=Monday..7=Sunday.
- Add versioned starter-program definitions and user-owned programs/workouts.
- Add dated `scheduled_workouts` and `scheduled_sets`; snapshot names, exercise
  order and targets rather than resolving the current template later.
- Introduce UUID-addressed `workout_sessions` and remove the effective
  `UNIQUE(user_id,date)` limitation. A date may contain the planned session and
  one or more off-plan sessions. Legacy `/logs/{date}` remains a compatibility
  view only; new mutations address session/workout UUIDs.
- Relate performed set data to an optional scheduled set; explicitly mark extra
  sets so they never satisfy required completion.
- Store day outcome separately with `participated`, `finalized_at`, and the
  timezone/date basis used at finalization.
- Performed and scheduled sets own immutable exercise name/category/modality
  snapshots; provenance IDs are nullable and never cascade-delete history when a
  mutable template/program exercise changes.
- Add idempotency records plus monotonic resource revisions. Mutation payloads
  carry stable operation keys and `expected_revision`; repeated matching payloads
  return the stored result and stale revisions return 409 with the authoritative
  resource.
- Every user-owned table enforces ownership in DAO queries.
- Account deletion cascades or explicitly deletes every new owned table.

## Grounding

- Follow migration numbering after `migrations/011_create_set_logs.up.sql`.
- Follow model conventions in `internal/model/*.go` and DAO transaction patterns
  in `internal/dao/log_dao.go`.
- Keep all public JSON `snake_case` and update `docs/CONTRACTS.md` alongside model
  shapes so downstream work has one source of truth.

## DO / DON'T

- DO snapshot required targets on the dated workout.
- DON'T point scheduled history only at a mutable template/program row.
- DO permit multiple performed workouts on one date.
- DON'T collapse the original missed commitment into an off-plan workout.
- DO preserve existing-user data and expose an idempotent adoption operation that
  can copy legacy templates/weekly assignments into a user program/future week.

## Forward requirements

Slice 1.2 needs DAO interfaces for profile, starter listing, program CRUD,
schedule range reads/writes, required-set checks, and day-outcome finalization.
